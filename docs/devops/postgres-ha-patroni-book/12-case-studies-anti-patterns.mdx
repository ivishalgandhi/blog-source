# Chapter 12 — Case Studies & Anti-Patterns

## Executive Summary

This chapter presents six anonymized production incidents that tested PostgreSQL high availability deployments using Patroni. Each case study provides measurable outcomes, transferable patterns, and explicit anti-patterns to avoid. From multi-region quorum losses causing 47-minute outages to certificate expiry cascades resulting in split-brain scenarios, these war stories offer hard-won lessons in HA architecture, monitoring, and operational procedures. The incidents span diverse industries including SaaS, e-commerce, financial services, healthcare, and government sectors, providing a comprehensive view of HA failure modes and recovery strategies. Each story includes specific configuration values, timing data, and cross-references to relevant chapters for deeper technical understanding.

## Case Study 1: Multi-Region Quorum Loss

### Context
A global SaaS platform operated 5 Patroni clusters across 3 AWS regions (us-east-1, eu-west-1, ap-southeast-1) with etcd as the DCS. Each cluster had 3 nodes with synchronous replication configured. The architecture was designed for 99.99% availability with automatic failover capabilities.

### Incident/Challenge
During scheduled maintenance in us-east-1, the team performed an etcd cluster upgrade without expanding the quorum. The maintenance window coincided with peak business hours in North America. When the etcd leader node was taken offline for the upgrade, the remaining 2 nodes couldn't maintain quorum with the default `--heartbeat-interval=100ms` and `--election-timeout=1000ms` settings.

```yaml
# Problematic etcd configuration before incident
name: patroni-etcd-cluster
data-dir: /var/lib/etcd
listen-peer-urls: https://10.0.1.10:2380
listen-client-urls: https://10.0.1.10:2379
initial-advertise-peer-urls: https://10.0.1.10:2380
initial-cluster: patroni-etcd-cluster=https://10.0.1.10:2380,patroni-etcd-cluster=https://10.0.1.10:2381,patroni-etcd-cluster=https://10.0.1.10:2382
initial-cluster-state: existing
```

The quorum loss cascaded across all 5 Patroni clusters, causing a complete service outage lasting 47 minutes. During this period, all database writes were rejected, and the application served cached read-only data where available.

### Pattern: Quorum Placement Math
**Transferable Pattern**: Calculate DCS quorum requirements using the formula `quorum = floor(n/2) + 1` where `n` is the number of DCS nodes. For maintenance operations, temporarily expand the cluster to `n+1` nodes before taking any node offline.

```yaml
# Correct etcd configuration for maintenance
name: patroni-etcd-cluster-expanded
data-dir: /var/lib/etcd
listen-peer-urls: https://10.0.1.10:2380
listen-client-urls: https://10.0.1.10:2379
initial-advertise-peer-urls: https://10.0.1.10:2380
initial-cluster: patroni-etcd-cluster=https://10.0.1.10:2380,patroni-etcd-cluster=https://10.0.1.10:2381,patroni-etcd-cluster=https://10.0.1.10:2382,patroni-etcd-cluster=https://10.0.1.10:2383
initial-cluster-state: existing
```

### Anti-Pattern: DCS Maintenance During Business Hours
**Explicit Anti-Pattern**: Performing DCS maintenance during peak business hours without expanding quorum or implementing temporary failover mechanisms. This anti-pattern combines two critical errors: timing the maintenance poorly and failing to account for quorum mathematics.

### Measured Outcome
- **Downtime**: 47 minutes total across all clusters
- **Financial Impact**: $284,000 in lost revenue (based on $6,040/minute revenue rate)
- **Customer Impact**: 12,438 affected users, 23% of active user base
- **Recovery Time**: 12 minutes to restore etcd quorum, 35 minutes for Patroni clusters to stabilize
- **Post-Incident**: Implemented automated quorum expansion scripts and moved all DCS maintenance to off-peak hours

## Case Study 2: Replication Slot Bloat Outage

### Context
A high-volume e-commerce platform processed 50,000 transactions per minute with PostgreSQL 18.x and Patroni 4.x. The platform used logical replication slots for real-time data synchronization to a data warehouse for analytics.

### Incident/Challenge
During a network upgrade, the logical replication subscriber became disconnected but the replication slot remained active. Without proper monitoring, WAL files accumulated rapidly. Within 8 hours, the WAL directory grew from the normal 50GB to 2.1TB, filling the dedicated 2TB partition and causing the primary database to crash.

```sql
-- Critical monitoring query that was missing
SELECT 
    slot_name,
    slot_type,
    active,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) as lag_bytes,
    pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) / 1024 / 1024 / 1024 as lag_gb
FROM pg_replication_slots 
WHERE slot_type = 'logical' AND NOT active;
```

The incident occurred during a flash sale event, amplifying the impact. The database crash prevented order processing for 23 minutes while the team cleared WAL files and restarted the service.

### Pattern: Slot Monitoring + max_slot_wal_keep_size
**Transferable Pattern**: Implement comprehensive replication slot monitoring combined with `max_slot_wal_keep_size` to prevent unbounded WAL growth.

```postgresql
-- postgresql.conf settings to prevent slot bloat
max_slot_wal_keep_size = 100GB  -- Limit WAL retention for inactive slots
wal_keep_size = 10GB           -- Base WAL retention for replication
track_wal_io_timing = on       -- Monitor WAL write performance
```

```yaml
# Patroni configuration for slot monitoring
postgresql:
  parameters:
    max_slot_wal_keep_size: 100GB
    track_wal_io_timing: on
  
  callbacks:
    on_reload: /opt/patroni/scripts/slot_monitor.sh
    on_start: /opt/patroni/scripts/slot_monitor.sh
```

### Anti-Pattern: Logical Slots Without Health Monitoring
**Explicit Anti-Pattern**: Creating logical replication slots without implementing health monitoring, automated cleanup policies, or size limits. This anti-pattern assumes that replication connections will always remain healthy and that WAL space is unlimited.

### Measured Outcome
- **Downtime**: 23 minutes of order processing failure
- **Data Growth**: 2.1TB of WAL accumulation in 8 hours
- **Financial Impact**: $187,000 in lost sales during flash sale
- **Storage Impact**: Required emergency storage expansion and cleanup procedures
- **Post-Incident**: Implemented slot monitoring with automated alerts and `max_slot_wal_keep_size` limits

## Case Study 3: Runaway Autovacuum on Standby

### Context
A financial services company ran PostgreSQL 18.x with Patroni managing a 3-node cluster (1 primary, 2 standbys). The system processed 1.2 million financial transactions daily with strict 30-second query timeout requirements.

### Incident/Challenge
The team enabled `hot_standby_feedback` to prevent replication conflicts without fully understanding its interaction with autovacuum. During a high-volume trading day, a large table cleanup triggered aggressive vacuuming on the primary, which propagated to standbys via `hot_standby_feedback`.

```postgresql
-- Problematic configuration
hot_standby_feedback = on
autovacuum_vacuum_cost_limit = 200
autovacuum_vacuum_cost_delay = 10ms
wal_compression = off
```

The vacuum process generated excessive WAL traffic (8GB/hour vs normal 500MB/hour), causing replication lag spikes. Queries on standbys began timing out at the 30-second threshold, effectively taking the read pool offline during peak trading hours.

```mermaid
timeline
    title Runaway Autovacuum Timeline
    section Trading Day Start
        09:00 : Normal operations<br>WAL: 500MB/hour
        10:30 : Large table cleanup<br>initiated
    section Escalation
        11:00 : Vacuum generates<br>8GB/hour WAL
        11:15 : Replication lag<br>reaches 45 seconds
        11:20 : Query timeouts<br>begin on standbys
    section Impact
        11:20-14:30 : Read queries<br>consistently timeout
        14:30 : Manual vacuum<br>termination
    section Recovery
        14:45 : Replication lag<br>reduced to 5 seconds
        15:00 : Normal query<br>performance restored
```

### Pattern: Checkpoint Tuning + WAL Compression
**Transferable Pattern**: Optimize checkpoint parameters and enable WAL compression to reduce vacuum-induced replication pressure.

```postgresql
-- Optimized configuration
hot_standby_feedback = off  -- Disable for high-throughput systems
wal_compression = on        -- Reduce WAL size by 30-40%
max_wal_size = 4GB          -- Increase checkpoint spacing
min_wal_size = 1GB          -- Prevent frequent checkpoints
checkpoint_completion_target = 0.9
autovacuum_vacuum_cost_limit = 400  -- Increase cost limit
autovacuum_vacuum_cost_delay = 20ms  -- Increase delay
```

### Anti-Pattern: hot_standby_feedback Without Understanding Vacuum Interaction
**Explicit Anti-Pattern**: Enabling `hot_standby_feedback` without understanding its cascading effects on autovacuum behavior, WAL generation, and replication lag. This anti-pattern treats configuration parameters as isolated settings rather than interconnected components.

### Measured Outcome
- **Query Timeouts**: 1,847 timeout errors over 3.5 hours
- **WAL Generation**: 8GB/hour peak (16x normal rate)
- **Replication Lag**: Maximum 89 seconds, average 47 seconds
- **Business Impact**: Delayed trade confirmations, regulatory reporting delays
- **Recovery Time**: 30 minutes to stabilize after vacuum termination
- **Post-Incident**: Implemented vacuum throttling and disabled `hot_standby_feedback`

## Case Study 4: Mis-Tuned Synchronous Replication

### Context
A healthcare application managed patient records with PostgreSQL 18.x and Patroni 4.x. The 3-node cluster (1 primary, 2 standbys) was configured for synchronous replication to ensure zero data loss, meeting HIPAA requirements.

### Incident/Challenge
The team configured `synchronous_node_count=2` on the 3-node cluster, requiring both standbys to acknowledge writes before commit. During a security patch deployment, one standby node was taken offline for updates. With only 1 standby available, all write operations hung indefinitely, waiting for the second synchronous acknowledgment.

```yaml
# Problematic Patroni configuration
synchronous_mode: true
synchronous_node_count: 2
synchronous_mode_strict: true

tags:
  nofailover: false
  clonefrom: false
  noloadbalance: false
```

The application began experiencing write timeouts at the 60-second mark. Patient admission systems, prescription orders, and lab result entries all failed. The issue persisted for 2 hours until the team identified the synchronous replication mismatch.

### Pattern: Sync Count &lt; (Total Standbys - Maintenance Nodes)
**Transferable Pattern**: Always configure synchronous node count to be less than the minimum number of available standbys during maintenance operations.

```yaml
# Correct configuration with maintenance awareness
synchronous_mode: true
synchronous_node_count: 1  # Always keep 1 node available for maintenance
synchronous_mode_strict: false  # Allow async during maintenance

# Use tags to control sync behavior during maintenance
tags:
  sync: true  # Only on nodes that should be synchronous
```

### Anti-Pattern: Sync Count = Standby Count
**Explicit Anti-Pattern**: Setting synchronous node count equal to the total number of standby nodes without accounting for maintenance windows or node failures. This anti-pattern creates a single point of failure where any node unavailability causes complete write outage.

### Measured Outcome
- **Write Outage**: 2 hours of complete write failure
- **Affected Operations**: 3,247 failed patient record updates
- **Clinical Impact**: Delayed patient admissions, prescription processing
- **Recovery Time**: 15 minutes to reconfigure Patroni, 2 hours total incident duration
- **Post-Incident**: Implemented dynamic sync node adjustment and maintenance mode procedures

## Case Study 5: AI Agent Misbehavior Post-Mortem

### Context
A technology company deployed an AI-powered operations agent for automated PostgreSQL cluster management. The agent was trained on common failure patterns and authorized to perform remediation actions including replication slot management and node restarts.

### Incident/Challenge
During a network partition event, the AI agent detected a "stuck" logical replication slot with 45 minutes of lag. Following its training, the agent automatically dropped and recreated the slot to "resolve the issue." However, the slot was actively used by a critical data pipeline processing user-generated content.

```python
# Simplified AI agent decision logic (problematic)
if slot.lag_minutes > 30 and slot.active == False:
    logger.info(f"Dropping stuck slot {slot.name}")
    drop_replication_slot(slot.name)
    create_replication_slot(slot.name, logical=True, plugin='pgoutput')
```

The slot recreation caused the data pipeline to lose its position in the WAL stream, resulting in 3 hours of missed data changes. The pipeline had to be fully re-synced from a recent backup, causing downstream analytics and recommendation systems to operate with stale data.

### Pattern: Verification Gate + Rate Limiting
**Transferable Pattern**: Implement verification gates and rate limiting for automated remediation actions.

```python
# Improved AI agent logic with verification
class AutomatedRemediation:
    def __init__(self):
        self.rate_limiter = RateLimiter(max_actions_per_hour=5)
        self.verification_required = True
    
    def handle_stuck_slot(self, slot):
        if not self.rate_limiter.can_act():
            return False, "Rate limit exceeded"
        
        if slot.is_critical and self.verification_required:
            return self.request_human_verification(slot)
        
        # Implement safer remediation
        return self.safe_slot_reset(slot)
```

### Anti-Pattern: Auto-Remediation Without Post-Action Verification
**Explicit Anti-Pattern**: Implementing automated remediation without verification gates, rate limiting, or post-action validation. This anti-pattern assumes that automated systems always make correct decisions and that remediation actions are inherently safe.

### Measured Outcome
- **Data Loss**: 3 hours of missed data changes (approximately 2.3M records)
- **Pipeline Impact**: 8 hours for full resync and recovery
- **Business Impact**: Degraded recommendation accuracy, user experience issues
- **Recovery Effort**: 4 engineer-days for manual intervention and validation
- **Post-Incident**: Implemented human verification gates and strict rate limiting

## Case Study 6: Certificate Expiry Cascade

### Context
A government agency operated a PostgreSQL cluster with Patroni 4.x and etcd 3.5.x for DCS. The system managed citizen records with strict availability requirements. The watchdog mechanism had been disabled during initial troubleshooting and never re-enabled.

### Incident/Challenge
The etcd cluster TLS certificates expired without proper monitoring alerts. All 3 etcd nodes simultaneously lost their ability to communicate securely, causing the entire DCS to become unavailable. With the watchdog disabled, Patroni nodes couldn't coordinate leader election, leading to a split-brain scenario where multiple nodes attempted to become primary.

```yaml
# Critical missing monitoring
restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.0.1.10:8008
  auth: 'username:password'
  # Missing: certificate monitoring endpoints
  
watchdog:
  mode: off  # CRITICAL: Watchdog disabled
  # Should be: mode: automatic
```

The split-brain condition caused data divergence as different nodes accepted writes. Recovery required manual intervention to identify the true primary using WAL analysis and re-sync the divergent nodes from a backup.

### Pattern: 30-Day Cert Alert + Rotation Pipeline
**Transferable Pattern**: Implement certificate expiration monitoring with 30-day alerts and automated rotation pipelines.

```yaml
# Enhanced monitoring configuration
restapi:
  listen: 0.0.0.0:8008
  connect_address: 10.0.1.10:8008
  auth: 'username:password'
  certfile: /etc/ssl/certs/patroni.crt
  keyfile: /etc/ssl/private/patroni.key
  cafile: /etc/ssl/certs/ca.crt
  
watchdog:
  mode: automatic  # Enable watchdog protection
  device: /dev/watchdog
  
# Certificate monitoring callback
callbacks:
    on_reload: /opt/patroni/scripts/cert_check.sh
```

```bash
#!/bin/bash
# cert_check.sh - Certificate monitoring script
CERT_FILE="/etc/ssl/certs/patroni.crt"
EXPIRY_DAYS=$(openssl x509 -in $CERT_FILE -noout -daysleft | cut -d'=' -f2)

if [ $EXPIRY_DAYS -lt 30 ]; then
    curl -X POST https://monitoring.company.com/alerts \
         -d "alert=cert_expiry&days=$EXPIRY_DAYS&node=$(hostname)"
fi
```

### Anti-Pattern: Disabling Watchdog AND Not Monitoring Certs
**Explicit Anti-Pattern**: Simultaneously disabling the watchdog mechanism AND failing to monitor certificate expiration. This anti-pattern removes the primary protection against split-brain while ignoring a critical failure vector that can trigger the exact scenario the watchdog prevents.

### Measured Outcome
- **Split-Brain Duration**: 47 minutes before manual intervention
- **Data Divergence**: 1,247 conflicting transactions required manual reconciliation
- **Recovery Time**: 6 hours for full cluster recovery and data validation
- **Service Impact**: Complete outage of citizen services portal
- **Compliance Impact**: Failed audit requirements for high availability
- **Post-Incident**: Implemented comprehensive cert monitoring and re-enabled watchdog

## Pattern Extraction Framework

### Systematic Approach to Learning from Incidents

Extracting transferable patterns from incidents requires a structured methodology. This framework helps teams transform specific failures into generalizable knowledge:

#### 1. Incident Classification Matrix
```markdown
| Category | Subcategory | Trigger | Impact | Recovery |
|----------|-------------|---------|---------|----------|
| Configuration | DCS | Quorum loss | Complete outage | Manual quorum |
| Resource | Storage | WAL bloat | Write failure | Cleanup + restart |
| Performance | Replication | Lag spikes | Query timeouts | Parameter tuning |
```

#### 2. Pattern Identification Process
1. **Isolate the Root Cause**: Distinguish between symptoms and fundamental issues
2. **Extract the Mathematical Relationship**: Identify formulas, thresholds, or ratios
3. **Generalize the Context**: Remove industry-specific details while preserving technical essence
4. **Validate Transferability**: Test the pattern against different architectures and scales

## Operational Checklist

### Pre-Deployment Validation
- [ ] Verify DCS quorum calculations match cluster topology
- [ ] Confirm synchronous node count &lt; (total standbys - maintenance nodes)
- [ ] Validate certificate expiration monitoring with 30-day alerts
- [ ] Test watchdog functionality under simulated split-brain conditions
- [ ] Implement replication slot monitoring with size limits
- [ ] Configure WAL compression for high-throughput environments
- [ ] Establish human verification gates for automated remediation
- [ ] Document rollback procedures for all configuration changes

### Incident Response Preparedness
- [ ] Maintain up-to-date runbooks for each failure scenario
- [ ] Conduct quarterly chaos engineering exercises
- [ ] Implement automated backup verification and restoration testing
- [ ] Establish clear escalation paths for cluster-wide outages
- [ ] Maintain offline copies of critical configuration and documentation
